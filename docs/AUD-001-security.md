# AUD-001 authorization policy

Lyra keeps one local `~/Documents/lyra/` directory across Google accounts. A Google login does not authorize local files for upload. A note created by the Rust `create_note` command is bound only to the verified account active at creation. A note created without an account, copied into the directory, or restored by another program requires explicit consent before upload. Editing these files locally remains available.

Consent requests expose each logical note ID to the UI. The user starts with no notes selected, and Rust accepts only a unique subset of the current request for the verified account and session epoch. It rechecks identity and on-disk content before writing selected bindings. Unselected identities are remembered per account as declined and remain local; a new unrelated note does not reopen them. The explicit **Manage local notes** action rescans the directory and can reopen declined identities. Existing whole-request decline signatures remain readable and migrate to per-note decisions on a matching scan.

New app-created welcome notes have a persistent internal marker attached to their Rust-created logical identity and original content digest. The sync engine excludes that identity from consent, upload, remote conflict handling, and tombstones while the bytes still match. A successful changed save clears the marker; an external change retires the old identity on scan. A same-named older note without this evidence remains an ordinary note requiring consent. This conservative migration avoids excluding personal content by filename or approximate text.

The provenance ledger records a logical note ID, account bindings, and the last content digest. Rust records Lyra saves and renames. A content change found by a sync scan without a matching backend write retires the previous identity and requires consent again. This policy also applies to external edits. A legitimate Lyra save, including an atomic replacement, retains the logical ID. If ledger persistence fails, the local file remains and no new cloud authorization is granted.

Remote deletion is limited to a tombstone that names the verified account, retired logical note ID, and exact Drive file ID recorded in that account's binding. Existing tombstones without these fields remain inert. Deleting a local note while another account is active does not delete that account's remote note unless the local note is explicitly linked to it. For a note linked to two accounts, a local deletion affects only the active account's remote copy; the other account's copy remains available and can be downloaded on a later sync.

The ledger and manifest formats remain backward compatible through optional fields. Previously authorized notes keep their bindings while their content matches the recorded digest. Legacy manifest evidence is accepted only when no other account already owns the logical note. A newly created note may need one successful sync to record its Drive ID before a later local deletion can propagate remotely.

Filesystem metadata cannot always prove whether identical bytes were edited or replaced externally. Identical content poses no new content disclosure at the time of observation, but Lyra cannot guarantee semantic identity in that case. External processes do not participate in Lyra's file locks. Uploads use the checked byte snapshot, so a later external write cannot alter those upload bytes, although it can leave Drive temporarily behind the local file. The identity digest is MD5 for compatibility with existing manifests; a deliberate MD5 collision remains outside this guarantee. No real Google Drive operation is required for the local security tests.
