# F1 workspace migration review

The F1 note directory is unavailable until Rust reports a committed workspace with a valid `lyra/workspaces/ws_<id>` path. Neither Tauri note commands nor frontend path helpers choose the legacy root as a fallback. Directory resolution failures are shown by the migration gate and can be retried; they do not create an alternate library.

The recovery notifier registers and drains Rust's queued recovery events only after `WorkspaceGate` confirms a ready workspace and installs its notes path. A focus event before that point does not start recovery. The authorization dialog also mounts inside the gate. A missing workspace directory keeps the gate closed after restart; no note-dependent UI starts against an unavailable path.

The single-instance plugin runs before Tauri setup. A process-held lock in the app configuration directory also protects migration when Linux D-Bus session isolation prevents the plugin from seeing another process. The lock is acquired before any migration command advances the journal.

Google Drive content sync remains paused in Rust for all of F1, including installs with a missing journal. The immediate remote-trash path is also skipped. OAuth account management and local-only note actions are separate from content synchronization. F4 must bind Drive manifests, provenance, and archive operations to workspaces before enabling sync.

The migration captures the local archived projection from the old causal ledger before moving notes and seeds it into the first workspace under fresh local identities. An adopted destination with different content does not inherit the original note's archived state. The old causal ledger and preferences remain untouched in the root. If there is no old causal ledger, the existing `.preferences.json` `paper` value remains available for frontend legacy initialization. Remote causal operations and account bindings in the old root are **not migrated or activated** in F1; they remain preserved for later workspace-aware migration.

Drafts remain in localStorage during the Rust migration. For a note copied under its original name, the existing draft recovery flow remains available. For a conflict resolved as `KeepBoth` or `AdoptDestination`, the backend reports the old draft key. Before opening the editor, the frontend writes that draft to a uniquely named local-only recovery note with exclusive creation, reads it back, and only then removes the old key. Failure leaves the key intact and keeps the gate closed for retry. The dedicated Rust command never grants a Google account binding to the recovery note. A missing migration journal after completion can remove the conflict mapping from the snapshot; this exceptional recovery path still needs manual validation before release.

Retire conflicts are saved in the journal and shown after restart while the original remains in the root. Moving an original into `rescatados/` now reserves the backup name exclusively, so an existing backup cannot be overwritten. Hard-link based moves require source and backup directory on the same filesystem; failure leaves the original in place for explicit retry. A crash between hard-link creation and source removal can leave two accessible copies.

Manual validation remains required on Fedora and Windows 11: path resolution errors and retry, second launch (including separate Linux sessions), migration restart with a retire conflict, archived notes, drafts, and the migration gate in the actual Tauri WebView. Run these checks on a disposable copy of fictional notes. Do not enable real Drive sync or migrate the user's library during verification.
